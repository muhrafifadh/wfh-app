# 01 · Project Structure

Where files go, and which parts of the code may import from which.

## Layout

```
src/
├── app/                        # Routing only
│   ├── (auth)/                 # Route group: login, register (no app shell)
│   ├── (app)/                  # Route group: authenticated app shell
│   │   ├── layout.tsx
│   │   └── invoices/
│   │       ├── page.tsx
│   │       ├── loading.tsx
│   │       ├── error.tsx
│   │       ├── [id]/page.tsx
│   │       └── _components/    # Used only by this route
│   ├── api/                    # Route handlers (see 08)
│   ├── layout.tsx              # Root layout: <html>, fonts, <Providers>
│   ├── providers.tsx           # Client providers (theme, query client, toaster)
│   ├── not-found.tsx
│   ├── global-error.tsx
│   └── globals.css
├── components/
│   ├── ui/                     # shadcn primitives (generated by the CLI)
│   └── shared/                 # Composed components used across features
├── features/
│   └── invoices/               # One folder per domain
│       ├── components/
│       ├── actions.ts          # Server Actions        (see 09)
│       ├── queries.ts          # Server reads           (see 08)
│       ├── query-keys.ts       # TanStack Query keys    (see 08)
│       ├── schemas.ts          # Zod schemas            (see 10)
│       ├── search-params.ts    # nuqs parsers           (see 11)
│       ├── hooks.ts            # Client hooks
│       └── types.ts
├── lib/
│   ├── api/                    # Backend client (server-only)
│   ├── auth/                   # Session helpers (server-only)
│   ├── actions.ts              # ActionResult type + helpers
│   ├── env.ts                  # Validated env vars
│   └── utils.ts                # cn() and small pure helpers
├── hooks/                      # Client hooks shared across features
├── stores/                     # Zustand stores
├── types/                      # Types shared across features
├── config/                     # Static config: site metadata, nav, constants
└── proxy.ts                    # Request-level redirects (see 12)
```

A feature only creates the files it needs. Don't add empty `hooks.ts` or `types.ts` files just to fill the layout.

## Rules

- **`app/` is for routing.** Pages and layouts fetch data and arrange feature components. Business logic goes in `features/` or `lib/`.
- **Keep code as close as possible to where it's used.** Start in the route's `_components/` folder. Move it to `features/<feature>/` when another route in the same feature needs it. Move it to `components/shared/` or `lib/` when another feature needs it.
- **Imports only flow one way:**

  ```
  app  →  features  →  components/shared, hooks, stores  →  components/ui, lib, types, config
  ```

  Code may import from its own level or any level to the right. It must never import from a level to its left.

- **Features don't import from each other.** If `features/invoices` needs something from `features/customers`, move that code down to `components/shared`, `lib`, or `types`. The one exception is a page in `app/`: it may combine components from several features.
- **Don't use barrel files** (`index.ts` that re-exports a folder). They slow down builds and tree-shaking and cause circular imports.
- **Prefix private folders in `app/` with `_`** so Next.js doesn't treat them as routes.
- **Use route groups `(name)`** to give different sections different layouts. Don't use them just to organize files.

## Don't

- **Don't make `utils/` or `helpers/` folders inside features.** They fill up with unrelated code. Give the file a name that says what it does (`format-currency.ts`).
- **Don't put a component in `components/shared/` "because it might be reused".** Move it there when a second feature actually uses it.
- **Don't put business logic in `components/ui/`.** Primitives must not know about the domain.
- **Don't add top-level folders** that aren't listed above without first updating this doc.
